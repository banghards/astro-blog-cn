# Hermes能干什么

Hermes 不是一个更会聊天的 AI。

我更愿意把它理解成：让 AI 长期待在工作流里的运行环境。

普通聊天窗口的问题是，它大多只活在这一轮对话里。

你问，它答。

你关掉页面，很多上下文就断了。

Hermes 想解决的是另一件事：让 agent 记住项目，接消息，调工具，跑任务，必要时拆出子 agent，把工作留在一个持续运行的地方。

它真正能干的事，可以压成五类。

第一，记住项目。

Hermes 有持久记忆，也会读取项目里的上下文文件。比如 `.hermes.md`、`AGENTS.md`、`CLAUDE.md` 这类文件，可以告诉它这个项目怎么做事、有什么约束、哪些习惯不能破坏。

这和每次重新粘贴背景不一样。

如果你长期维护一个内容系统、一个代码仓库、一个运营流程，记忆和项目规则会比单次回答更重要。

第二，调用工具。

Hermes 不是只生成建议。它可以通过工具处理文件、跑终端、做 web search、开浏览器、接 MCP、调用外部 API。

这意味着你可以让它做“带动作的任务”。

比如不是问它“这个网页里有什么”，而是让它打开网页、翻页、抽取结构化信息，再把结果整理到文件里。

不是问它“这个仓库可能哪里有问题”，而是让它读文件、跑测试、改代码、留下 checkpoint。

第三，接住不同渠道来的任务。

Hermes 可以通过 CLI，也可以接 Telegram、Discord、Slack、WhatsApp、Signal、WeChat、Email 这类渠道。

这个点的重点不是“渠道很多”。

重点是 agent 不必绑在一个浏览器标签页里。

你可以在手机上丢一个任务，它在服务器上继续跑；你晚点回来，再看结果。

第四，跑定时任务。

这是我觉得最容易被低估的能力。

很多 AI 工作不是一次问答，而是固定频率的重复检查。

每天早上抓一组信号。

每周整理一次反馈。

每隔几小时检查某个页面、仓库、指标或舆情。

这些事用聊天窗口做很别扭，因为你每次都要重新发起。

但放到 Hermes 这种常驻 agent 里，它就更像一个可调度的工作节点。

第五，拆分长任务。

Hermes 支持子 agent。大任务可以拆成几个并行的小任务，每个子 agent 有自己的上下文和工具范围。

这适合研究、代码检查、内容拆解、批量处理。

比如你要写一篇长文，可以让一个 agent 查资料，一个 agent 看竞品，一个 agent 整理你的旧内容，最后主 agent 合并判断。

但这里也要小心。

子 agent 越多，越需要明确边界。

不然它只是把混乱并行化。

所以我不会把 Hermes 理解成“自动员工”。

它更像一个工作台。

上面放着模型、工具、记忆、浏览器、终端、消息入口、定时任务和安全回滚。

你能把一些重复动作交给它。

但你不能把责任交出去。

我觉得 Hermes 适合三类场景。

第一类是信息整理。

比如定时抓取几个信息源，去重，摘要，按主题分类，再把值得看的部分发到你的消息渠道里。

它不是替你判断世界发生了什么。

它是先把材料筛到桌面上。

第二类是内容系统。

比如你有 inbox、brief、draft、score、feedback 这样的目录。

Hermes 可以帮你把一个想法变成 run，补齐 brief，生成第一版 draft，做 anti-AI 味检查，最后提醒你看 24 小时数据。

但它不应该直接替你发布。

因为能不能发，是你的判断。

第三类是代码和运维辅助。

比如读项目规则，检查 diff，跑测试，修一个小 bug，或者定时看某个服务状态。

它可以把很多机械步骤串起来。

但涉及生产权限、删除、付款、对外承诺的动作，应该有人工确认。

这就是 Hermes 的边界。

它适合做长期运行的调度层，不适合做无人看管的最终决策者。

如果你只是偶尔问几个问题，不需要 Hermes。

普通聊天窗口够用。

如果你要的是：

- 任务能跨天继续
- agent 能记住项目规则
- 能通过消息渠道收任务
- 能定时跑检查
- 能调用浏览器、终端、文件、MCP
- 能把大任务拆给子 agent
- 能把可复用经验沉淀成 skill

那 Hermes 才开始有意义。

我对它的判断很简单：

不要把 Hermes 当成“更强聊天机器人”。

把它当成一个能长期运行的 AI 工作台。

聊天只是入口。

真正值钱的是它能把入口后面的工具、记忆、任务和反馈接起来。
