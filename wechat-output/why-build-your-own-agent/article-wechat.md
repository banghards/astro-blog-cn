# 为什么我还是劝你自己搭一个 Agent，哪怕 OpenClaw 和 Hermes Agent 已经够好了

最近一两个月，个人 Agent 这条线越来越热。

今天是 `OpenClaw`，明天是 `Hermes Agent`，后天又冒出来一个更轻、更快、更多功能的新框架。你刷一圈社区，很容易产生一种感觉：

既然现成的已经这么强了，为什么还要自己搭？

这个问题很合理。

而且说实话，大多数人第一次看到那些“3 分钟装好一个全能 Agent”的演示时，都会有一点动摇。

既然别人已经把轮子造好了，自己还折腾什么？

但我越来越觉得，真正值得你自己搭的，不是一个“功能更多的助手”，而是一个 **会随着你的工作方式一起长大的系统**。

这两者表面上看起来很像，实际上完全不是一回事。

![自己搭个人 Agent 的像素风封面图](./illustrations/01-cover-wide.png)

---

## 先说结论：我不是反对 OpenClaw 和 Hermes Agent，我是反对把主动权交出去

先把立场摆清楚。

`OpenClaw` 也好，`Hermes Agent` 也好，都是很好的项目。

如果你之前没认真用过个人 Agent，它们其实都是非常好的起点。  
你甚至完全可以先从它们开始。

但我真正想说的是：

**起点很好，不代表你永远都该停在起点。**

因为当你的 Agent 搭在别人的框架上时，你获得的是一套能力；  
但同时，你也把很多关键的东西一起托管出去了：

- 底层怎么演进，不由你定
- 数据格式怎么设计，不由你定
- 哪一层可以替换，哪一层绑死，不由你定
- 下一次迁移要不要花一周，往往也不由你定

也就是说，你用的不只是工具，你还顺带接受了一整套别人替你做好的结构决定。

而自己搭，最大的价值不在于“代码都是自己写的”，而在于：

**你终于可以决定，什么该变，什么不该变。**

---

## 第一个原因：自己搭的 Agent，不需要一开始就完美，它可以跟着你的需求一起长大

很多人一想到“自己搭 Agent”，脑子里马上出现的是一个很重的任务：

- 要懂 LLM 编排
- 要懂工具调用
- 要懂记忆系统
- 要懂异步
- 要懂部署

最后越想越觉得，这不是普通人该碰的事。

但现实往往没那么夸张。

真正的个人 Agent，通常不是一开始就被设计成一个完整系统的。  
它更像是一个先能跑、再慢慢长的东西。

你先搭一个最小版本。

它也许一开始只会：

- 接消息
- 调模型
- 做几个简单动作

然后你开始往里加东西：

- 加一层记忆
- 加一个定时任务
- 加一个自己的技能
- 再加一个常用入口

慢慢地，它就不再是“一个 demo”，而是一个会越来越贴近你日常工作的系统。

这件事的关键在于：

你不是先设计一个完美框架，再去填功能；  
你是先让它参与工作，再让它在工作里生长。

这和直接装一个别人做好的框架，有很大区别。

现成框架给你的，是一个“已经定义好的能力集合”。  
自己搭给你的，是一个“可以随着你变化而变化的结构”。

---

## 第二个原因：你用别人的框架，很容易一直卡在“配置层”

这几个月个人 Agent 生态有一个很明显的现象：

每隔一段时间，就会出现一个新的“更好方案”。

然后很多人的状态就变成：

1. 花两天装环境
2. 花三天调 prompt
3. 花几天修记忆和工具链
4. 刚顺手一点，又看到新的方案出来
5. 然后重来一遍

这其实是一种非常典型的“注意力税”。

你以为自己在升级工具，实际上你一直在为工具换代付出迁移成本。

而最麻烦的地方在于：

**你看起来一直在前进，其实很可能一直停在配置层。**

环境在换，prompt 在换，框架在换，但真正跑到应用层、跑到自己工作流里去的东西并不多。

这就是为什么我越来越在意一件事：

不是哪个框架“现在最强”，而是我有没有能力让自己的系统只换我想换的那一层。

比如底层编排换掉，但入口层不动；  
比如 provider 换掉，但记忆格式不动；  
比如模型换掉，但技能接口不动。

这种自由度，才是真正能把迁移成本压下来的关键。

否则你永远在重新装修，却从来没有真正住进去。

## 第三个原因：自己搭过一次之后，你看别人框架的方式会彻底变掉

我觉得这是很多人一开始意识不到，但后面会越来越明显的事。

当你只是“用”一个框架时，你看到的是一个整体：

- 这个项目好不好用
- 这个框架强不强
- 这个功能多不多

但当你自己真正搭过一遍之后，你再看别人的项目，就不再是“整体崇拜”了。

你会开始自动拆层。

你会问的不是：

“这个框架值不值得全盘迁移？”

而是：

- 它的技能目录设计是不是比我好？
- 它的依赖预检机制能不能拿过来？
- 它的多 provider 抽象是不是更干净？
- 它的记忆持久化有没有某一层值得借鉴？

这时候你再研究开源项目，不是在找“信仰”，而是在找“零件”。

这就是自己搭 Agent 特别有价值的一点：

**你获得的不是某个单一工具，而是一种拆解、重组、重构个人系统的能力。**

你开始能看出：

- 哪一层只是表面酷
- 哪一层是真正省心
- 哪一层现在看起来不重要，但规模一上来就会爆

只有自己搭过的人，才会天然开始这样看问题。

![从别人的框架里偷零件，装成自己的系统](./illustrations/03-steal-components.png)

## 第四个原因：2026 年自己搭 Agent 的门槛，比很多人想象中低太多了

很多人不自己搭，不是因为不想，而是因为一听到“自己搭”，就默认这件事很硬核。

但现在有一个很现实的变化：

你已经不需要像以前那样，先自己把所有代码写出来，才有资格拥有自己的 Agent。

你完全可以从非常小的改动开始。

比如：

- 觉得它太啰嗦，就改一行 system prompt
- 觉得它不懂你的缩写，就给它加一个内部词汇文件
- 觉得它老忘事，就补一层轻量记忆
- 觉得它不会主动提醒你，就让 AI 帮你写一个定时脚本

注意，这里面真正需要你做的，不是“会写所有代码”，而是：

**你要知道自己想让这个系统变成什么样。**

剩下那部分实现，现在已经可以大量交给 `Claude Code`、`Codex` 这类工具去协助完成。

这也是为什么我越来越觉得，2026 年是一个分界线。

以前“自己搭 Agent”更像工程师行为。  
现在“自己搭 Agent”更像是：

你定义效果，AI 帮你写实现，你再持续迭代。

也就是说，门槛真正下降的地方，不只是代码生成变强了，而是：

**你第一次有可能在不全栈精通的前提下，逐步拥有自己的系统。**

---

## 第五个原因：这不是技术主权的问题，而是你对自己工作方式的主权

我越来越相信一句话：

**如果一个系统不真正受你控制，它迟早会在最关键的地方反过来限制你。**

这件事放在个人 Agent 上尤其明显。

因为 Agent 不是普通工具。

它会越来越多地接触：

- 你的日程
- 你的文档
- 你的工作节奏
- 你的个人偏好
- 你的长期记忆
- 甚至你对某些项目的判断方式

这些信息加在一起，远比一个浏览器历史记录更敏感。

所以真正关键的问题，不只是“它能不能跑”，而是：

- 数据在哪里
- 记忆怎么存
- 格式谁定义
- 迁移权在谁手里

当这些事情全都建立在别人定义的框架之上时，你看起来是在使用一个工具，实际上是在把自己的工作方式逐步编码进别人给你的边界里。

而自己搭的价值就在于：

你不一定从第一天就拥有最强功能，  
但你从第一天开始，就保留了以后怎么改、怎么迁、怎么接着长的决定权。

这不是控制欲。

这是主权。

## 所以我真正建议的，不是“别用现成框架”，而是“别停在只会用现成框架”

如果你现在还是第一次接触个人 Agent，我其实一点都不建议你从零硬开。

最好的顺序反而是：

1. 先用 `OpenClaw` 或 `Hermes Agent` 跑起来
2. 认真用两周
3. 把真正让你烦、让你满意、让你觉得“差一点”的地方记下来
4. 从一个最小改动开始，把它变成更像你自己的东西

可能是一行 prompt。  
可能是一个词汇表。  
可能是一层记忆。  
可能是一个定时任务。  
可能是一个只服务你自己的技能。

你不需要一口气从“用户”跳到“框架作者”。

你只需要开始做第一个属于你的改动。

改着改着，你就会发现一个很微妙的变化：

它一开始是别人的工具，后来慢慢变成了你的系统。

这一步，往往不是靠一个宏大决定完成的，而是靠一连串很小、但持续的定制完成的。

---

## 最后一句话：你不是在搭一个更厉害的助手，你是在搭一个越来越理解你的系统

这大概是我最想说的。

为什么我还是劝你自己搭一个 Agent，哪怕现在现成框架已经很好？

因为你真正需要的，往往不是“社区里最火的那个 Agent”，而是一个会越来越贴合你工作方式、越来越懂你、并且进化主动权始终在你手里的系统。

现成框架给你的是起点。  
自己搭，给你的是方向盘。

如果你只是想体验一下个人 Agent，先用现成的，完全没问题。  
但如果你真的准备长期把它接进自己的工作流，那迟早有一天，你会想把它往“更像你”的方向推一步。

而那一步，就是你开始拥有自己的 Agent 的起点。
